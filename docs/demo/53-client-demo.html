Ticket #53 · 驗收點

平行開工:三張票同時做,做完一張張合回主線

這一片要做的事:你點頭之後,三張互不相干的票各自拿一份獨立的專案副本開工,各自做完各自驗過,再一張一張合回主線,合完整批再驗一次,最後回報「3 張已合併」。

先講清楚:哪些是真的跑過的

QA 這一輪把底下每一塊零件都實跑驗過了 — 三個工作區真的互相看不到對方的檔、三張真的一張一張合回主線、合完的主線上整批驗證全綠、中文和 emoji 沒有壞碼、貼回票上的那條路真的貼上 GitHub。

但最上面那一層沒有跑過:你點頭之後,每個工作區裡真的去做那張票(build + QA)。QA 生不出等價物 — 那需要三張真的票、你真的點頭、三個 agent 真的做完。所以下面第 1 條和第 3 條,你會看到「只驗到零件」和「沒跑過」的標記,那不是壞掉,是沒被執行過。

擋著不能上線的問題:0 條。另外有 2 個小問題帶著給你看,在最後一段。

三張、各一行、各自不同的工作區。中文和 emoji 在把環境刻意調成舊編碼的情況下照樣沒壞。

「工作區真的互相看不到對方」怎麼驗的

QA 在一份拋棄式的專案副本上真的開了三個工作區,各自改各自的檔案、各自送出。第三個工作區裡去撈「所有人的檔案」,只撈得到自己那一個 — 另外兩個的檔案根本不存在。

但是:上面那三行字是程式印的「指示」,真正開工作區的 git 指令是照著那行字手打的。「跑這個指令就會得到那個工作區」這條因果,要等真的跑一次才連得起來。

3 張已合併,下一步:`/client-demo #51`(Codex: `$client-demo #51`) — 一次 demo 這批
合併那一段真的做過一次

QA 在拋棄式副本上真的把三張一張一張合回主線 — 不是同時。三次合併的紀錄首尾相接,對得上帳;每合完一張,那張的工作區當場收掉(三份 → 兩份 → 一份 → 沒了),不會三份一路佔著硬碟。

合完之後在主線上又把整套檢查跑了一次,全綠 — 這關就是在吃「各自都對、合起來壞」的風險。

一個誠實的但書:「3 張」這個數字是把輸入的張數印回來,程式本身不會去數真的合了幾張。真的合併有沒有發生,靠的是上面那段紀錄。

下一步:`/client-demo #51`(Codex: `$client-demo #51`)

三張票的驗收項合起來會自動去重,重複的只列一次。

這條為什麼標「沒跑過」

上面那則總結是真的貼上 GitHub 過一次(在 #53 這則 comment),撈回來一字不差 — 所以「字貼得上去」這條路是通的。

但貼的是 QA 造的假資料、貼在 #53 而不是真的母票 #51;而「每張票上的產出紀錄」是各工作區裡的 build 貼的,這一輪根本沒跑 build。所以整條驗收項的實際成果,零實錄。

帶著看的小問題

2 個 known issue,都不擋上線

兩個都已經開好票了。下面是我的建議處置,你整批看過,有意見的挑出來講。

票是什麼建議
#61 整批收尾時會做一次「清乾淨了沒」的檢查,但這台機器上永遠報「沒清乾淨」— 因為 Claude Code 自己有幾份常駐的工作副本住在同一個專案裡,被誤算進去了。 現在修 — 每跑一次批次就被送去查一個不存在的問題;反過來真的有殘留時也看不出來,等於這道檢查是壞的。
#62 操作手冊裡三處同型的指令,兩處寫得可以直接複製貼上,最後一處要 agent 自己拼。 現在修 — 功能是通的,但「照文件逐字跑」正是先前那個亂碼 bug 的來源;而且這兩張剛好可以拿來當下面那件事的實測材料。
要你決定

那個沒跑過的一層,現在補嗎?

第 1 條和第 3 條缺的是同一件事:真的跑一次 /build-batch — 拿真的票、你真的點頭、工作區裡真的做完 build + QA。這是這張票最核心的一層,也是自動檢查怎麼樣都補不到的一層。

  • 我推薦:現在就拿 #61 + #62 真跑一次。 這兩張本來就要修,順手變成這一片的實測材料 — 一次做完兩件事。代價是這一輪 demo 會拉長,而且它們改的是同一份文件,可能撞在一起 — 撞車處理是後面 #55 才做的,真撞上我會停下來手動解掉、留紀錄。
  • 或者:換兩張不會撞的票(例如 #42 + #47),乾淨地驗這一層,#61 / #62 之後另外修。
  • 或者:先過關,那一層等下一片(#54 一張沒過 QA)順便一起驗。你接受「這一層目前只有零件級證據」就行。
