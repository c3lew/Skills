# PM 訪談紀律

跟 client 談話的規則書。pm-intake 主用;wayfinder map 的 HITL ticket 引用;maintain 進件時走的 mini-intake 是輕量版 — 一樣過兩軸,但只問到「夠開一張票」就收。被引用的 skill 在 SKILL.md 開頭指向本檔,規則改一處全體生效。

## 大原則

把使用者當 **client**,不當工程師。問他的只有:使用者看得到的行為(功能、長相、操作感)+ 會影響他的現實取捨(花錢、拖時間、資料放哪)。技術決策系統自己拍板、自己留紀錄(見 `tech-decisions.md`),並翻成白話讓他看得懂。

## 兩軸對齊測試

每個待決節點過兩軸,決定「問 client」還是「自動拍板」:

- **影響軸**:選錯了使用者會不會親身受影響?
- **不確定軸**:LLM 有沒有把握知道使用者會怎麼選?

| | 有把握 | 沒把握 |
|---|---|---|
| **有影響** | 自動拍板,進收斂回合回報清單 | **必須問** |
| **沒影響** | 自動拍板,只留紀錄 | 自動拍板,只留紀錄 |

核心原則:**LLM 替使用者做決定的前提是它真的知道使用者會怎麼決定** — 沒把握就去問。

技術本質的題落在「必須問」象限時,翻成後果/情境語言再問:問「這套會在沒網路的內網跑嗎?」,不問「要不要 cloud storage?」。

## 問法節奏

- 每輪 **≤3 題**。
- **開放情境題優先**:「你平常怎麼處理 X?」勝過「要 A 還是 B?」。選擇題只用於真二選一。
- 避免「每題都選推薦」的點頭疲勞 — 那會複製 sycophancy:agent 自問自答。問題要讓 client 講出 agent 不知道的事,不是幫 agent 背書。
- 給選項時仍要給推薦 + 一兩句為什麼 + 代價(client 有權直接採納,但問題設計不能只剩採納)。

## 收斂回合(進 spec 前一次做完)

1. **自動拍板白話清單**:所有「有影響+有把握」的拍板,按白話三行制(見 `tech-decisions.md`)列出,含後果 — 這是 client 的否決點。
2. **Devil's advocate pass**:講出「這個功能最可能白做的理由」+ 更便宜的替代方案,client 明確回應才放行。
3. **成本標注**:相對量級(T-shirt size + 相對錨定,例「比上一片大一號」)+ 後果描述。**不給假精確時數**(METR RCT:LLM 時程預估系統性過度樂觀)。
4. **驗收清單拍板**:從 spec 生成 Gherkin scenarios 的白話版,client 逐條拍板 — 這份清單之後是 QA 的唯一 oracle。

## 語言

對話與文件用繁體中文,技術名詞保留英文;對 client 的所有輸出過「非技術也看得懂」的檢查 — 出現架構術語就重寫。
