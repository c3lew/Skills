==== W2 撈出來的 6 種候選,逐筆判讀 ====

全部 6 種都是**誤報**,原因同一個:W2 刻意只用「抓到下一個空白為止」這種最笨的
斷詞,不排除標點,所以票號後面黏著的收尾字元一起被抓進來了。逐筆:

1. `##`  x18
   來源:summary mode 的第一行 markdown 標題 `## 批次總結(2 張)`。
   判讀:誤報。這個 `#` 根本不是票號,是 markdown 的 heading 標記。W2 沒有像
   129-wide.py 的 HASH_RE 那樣寫 `(?<!#)#(?!#)` 去躲標題 —— 這支寧可撈進來人工
   看過,也不要先開一個「有 `##` 就跳過」的洞。

2. `#108`(Codex:`  x90
   來源:`` `/client-demo #108`(Codex: `$client-demo #108`) `` 這一句 —— 票號
   `108` 後面緊接反引號、全形括號、`Codex:`,中間都沒有空白。
   判讀:誤報。真正要量的那一段(反引號**裡面**)是 `/client-demo #108`,由 W1
   量,W1 是 0 筆違例。W2 抓的是反引號外面那一坨黏在一起的字。

3. `#108`)`  x54
   來源:同上,只是這一句的收尾是 `` `)`` 而不是接 `(Codex:`(merged 全綠 /
   merged 有人還在修 / summary 三個形狀的句尾)。
   判讀:誤報,理由同 2。

4. `#108`)會接續這條`  x36
   來源:interrupted 那句 `重跑 `/build-batch #108`(Codex: `$build-batch #108`)
   會接續這條 lane` —— 中文句子不打空白,所以整串黏成一坨。
   判讀:誤報,理由同 2。

5. `#48`(Codex:`  x18
6. `#48`)`  x18
   來源:merged 有人還在修那半的 `下一步:`/build #48`(Codex: `$build #48`)`。
   判讀:誤報,理由同 2 —— 這裡的票號是 `48`(fixing 那張),形狀跟 spec 那格
   一模一樣,黏標點的方式也一樣。

小結:W2 撈到 6 種 / 234 次,判讀後 **0 筆是真的問題**,全部是「中文與 markdown
的標點不打空白」造成的斷詞誤差。反過來這也是這支寬度的下界證明:如果 `#` 後面
真的出現空白(`# 108`,#130 出廠時的形狀)或小數(`#108.0`),W2 抓到的會是
`''` 與 `'108.0'`,一樣會被撈出來 —— 修前對照(130-prevdiff.txt)裡就是這樣紅的。
